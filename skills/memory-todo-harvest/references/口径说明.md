# 口径说明

本技能**怎么理解你的记忆文件**。看懂它，就知道清单里每一条为什么在那儿、为什么不在那儿，
也知道该在哪些地方调整。

---

## 一、什么算「待办」

只认三类显式信号，其余一律不进：

| 信号 | 形态 | 说明 |
|---|---|---|
| 待办语义章节 | `## 待办` / `### 下一步` / `### 未完成` / `### 遗留项` … | 章节内的列表项逐条入账，章节标题只作「出处」 |
| 未勾选 checkbox | `- [ ] 要做的事` | `- [x]` 视为已完成；所有文件类型都认，包括指令/规则文件 |
| 行内待办句 | `**待办**：…` / `剩余待办：…` | 可写在行中间；带 ①②③ 编号的自动拆成多条 |

**为什么不用章节标题当待办单位**：会话记录里的章节标题描述的是**已经发生的事**，
天然绝大多数已完成。用它当待办，真实待办会被淹没——量级差可达 50 倍。
代价是记忆文件里得真的写了标记，所以技能里同时提供了书写约定。

---

## 二、为什么长期档案只取「显式信号」

`MEMORY.md`、`AGENTS.md`、`CLAUDE.md` 这类文件同时装着**长期规则正文**与**真正的待办清单**。
如果把它们的章节正文整段当待办，会把规则条目也捞进来。

所以这类文件按「长期档案」处理：**只认未勾选 checkbox 与「待办：」标记行**。
注意 checkbox 是例外——它是显式标记、零歧义，**任何文件都认**。

---

## 三、状态怎么判

- 状态信号**只作用于待办正文**，不作用于整行。
  整行常含描述**前文**的「已发布 / 已完成」，用它判定会污染结果。
- 正文带「已完成 / 已修复 / 已上线」类信号 → 已完成
- 正文带「未做 / 待确认 / 下一步 / 进行中」类信号 → 未完成
- 正文带「已放弃 / 搁置 / 不采纳」类信号 → 终止（不进当前待办）
- **无任何信号 → 默认未完成**

最后一条是刻意设计：待办是「要做的事」，默认未完成才符合直觉。

---

## 四、为什么不自动判断「已完成」

**做过这个尝试，结论是不做。**

记忆文件是**只增不改的流水账**——做完了通常不会回头改原条目，
所以最强的「同位置状态变更」信号天然不存在。可行的旁证只有四类：

| 旁证 | 局限 |
|---|---|
| 后续日志里出现同名条目标题且带完成信号 | 措辞重叠度低，召回极少 |
| 待办提到的产出物已存在 | 弱证据，几乎无判别力 |
| 长期档案里的标记是否还在 | 只覆盖长期档案，能判定的条数有限 |
| 待办所在行附近出现完成痕迹 | 邻域常并置多件事，误报为主 |

四类合起来，可靠召回率只有个位数百分比；而阈值放低只会换来更多误报。
**误判的代价是错误关闭真实待办**——比不判更糟。

所以：判定权交给人工（页面勾选），持久化靠独立判定档案，
根治靠源头习惯（完成就把 `- [ ]` 改成 `- [x]`）。

## 五、归属怎么定

按**加权打分、取最高分**；同分取更具体的信号：

| 信号 | 权重 | 说明 |
|---|---|---|
| 标题 | 6 | 条目自己点名了项目，最可信 |
| 上下文 | 5 | 「待办：」之前的加粗片段 |
| 项目锚 | 5 | 向上回溯最近的「带项目名的章节标题」 |
| 文件主题 | 3 | 全文件出现最多的带项目名标题 |
| 目录 | 2 | 记忆目录的**上级目录名**（容器目录跳过） |

**项目锚为什么要回溯**：记忆文件里，项目名通常只出现在**段首标题**，
后面的同级标题（如 `## 17:37 · 第二轮联调`）不含项目名。
锚的作用就是让这些段落仍然知道自己在哪个项目下。
超过距离阈值（默认 400 行）视为失效，降权后交给文件主题兜底。

---

## 六、为什么「未分类」要留着

**不设兜底项目。** 给一个「其他」筐看起来能让「未分类 = 0」，
但它会把错误藏起来——条目全挤在一个筐里，页面上一大半看不出归属，
而使用者会误以为已经整理好了。

**错误的归属比诚实的未分类更糟。**
未分类不为 0 时的正确反应是：**先查项目台账有没有缺项，再怀疑算法**。

## 七、人工判定与产物的关系

| 载体 | 角色 | 会不会被重建 |
|---|---|---|
| `todos.json` | 归集产物 | 每次运行全量重建 |
| `todo-state.json` | 人工判定档案 | 只有人工操作会改它 |

判定优先级：**独立档案 > 产物内人工标记 > 日志信号 > 默认未完成**。

两者每次归集**双向对齐**：产物里有人工标记而档案没有 → 补档；
产物里已取消而档案还有 → 撤档。这样无论产物怎么重建 / 回滚，人工判定都不会丢。

---

## 八、为什么不自动回写记忆文件

**默认不回写。** 记忆文件是人（或 agent）手写的，脚本改动有覆盖人工校改的风险；
并行会话写同一文件还可能静默覆盖。一旦回写错误，原始信息就被污染且难以追溯。

判定落在独立档案，持久性等价，但**零污染风险**。
如果确实要回写，建议只做最小替换（`- [ ]` → `- [x]`），不做整段重写。

---

## 九、为什么用 JSON 文件而不是数据库

条目量在几十到几百条量级，JSON 足够；而且**可人工查看、可 diff、可备份**——
在机制还在调整、随时要排查的阶段，这个价值很高。
写盘一律**原子替换**（写临时文件再改名），避免中途失败留半个文件。

上到几千条、或需要并发写时，再考虑换 SQLite。

## 十、三类信号各自要配的防护

识别三类信号时，有四条必须同时做到——少一条就会稳定出错：

1. **行内标记必须用「搜索」而不是「行首匹配」** —— `**待办**：…` 常写在行中间
   （如 `…说明。**待办**：具体事项`），按行首匹配会永远漏掉这一类。
2. **状态只看待办正文，不看整行** —— 整行常含描述**前文**的「已发布 / 已完成」，
   拿整行判状态会把新待办误标成已完成。
3. **排除行内代码里的标记** —— 文档在举例说明「待办：」怎么写时，
   那个示例本身会被当成真待办捞走。写示例请包在反引号里。
4. **待办章节判定要严格** —— 章节名以「待办」开头但在讲别的事
   （如「待办清单整理」），不能算待办章节，否则整节内容被逐条捞走。

另外两项清洗：正文去 markdown 标记 / 前导时间戳 / 长度封顶；
**凭据掩码**（清单里不出现密码、token 明文）。

## 十一、人工判定为什么丢不了：三层兜底

机器抽取一定有错收与漏判。关键不是消灭错误，而是让错误**可发现、可撤回、可持久**。

**① 候选制** —— 机器**新**提名的待办先进「新发现 · 待确认」区，确认才转正、忽略进黑名单。
首次全量不做候选（否则要手点几十上百条），**只对增量生效**。

**② 独立判定档案** —— 判定另存 `todo-state.json`，与归集产物解耦（见 §七）。

**③ 判定跟着条目走：两条匹配通道** —— 条目 id 由「文件路径 + 标题」派生，
**标题改一个字 id 就变**，判定会失效。所以归集时要把旧判定找回来，用两条通道并行：

| 通道 | 算法 | 阈值 | 治什么 |
|---|---|---|---|
| 相似度 | Jaccard（交集 / 并集） | 同一记忆文件 ≥ 0.6；跨文件 ≥ 0.85（先打 0.9 折） | 改字、错字一类一般微调 |
| 包含关系 | 重叠率（交集 / 较小者） | 同一记忆文件 ≥ 0.9，且短串 ≥ 6 字 | **长尾补语被删**——此时 Jaccard 会跌破 0.6 |

重叠率单独用会让短标题对长标题虚高，所以它只作**受限补充**：
仅同文件、短串够长才启用，**跨文件一律走 Jaccard**。

命中后判定会**自愈迁移**到新 id（取消勾选、忽略黑名单两条路径都迁移），下次起精确命中。

**取向：宁可不匹配（人工再勾一次），也不误匹配（错误关闭真实待办）。**

> 常见症状对照：**勾过的条目过一阵又变回未完成 / 已忽略的又重新冒出来** ——
> 先看是不是刚改过记忆文件里那条待办的文字。改文字不会丢判定，但改到两条通道都认不出
> （比如把标题整句重写）就会退回未完成，人工再勾一次即可。

## 十二、事由标签怎么净化

「事由」取的是「待办：」之前的加粗片段或所属章节，用来回答「这条为什么留着」。
不净化会出现「事由：下一步」这种没信息量的标签。净化顺序：

1. 剥前导时间戳（`17:37 · `）、括号补充、破折号后缀
2. 优先取引号 / 反引号里的内容
3. 排除文档结构词——`未完成 / 下一步 / 待办 / 结果 / 产出 / 结论 / 验收 / 备份 / 归档`
   是**文档骨架，不是项目名**，命中即丢弃
